# xtrm-app

Linux-first desktop application workspace for XTRM's human ↔ agent interface.

**Status:** design/starter implementation, not a build-complete desktop app. The
canonical design is `docs/xtrm-gui-prd.md`; the current interaction unit is
**Frame** (`InteractionFrame`). This package is also the implementation root for
**XTRM Console v2** (PRD §34); start from [`docs/README.md`](docs/README.md).

## Product boundary

```text
human input
  ↓
provider session (Pi first, Claude adapter later)
  ↓
InteractionFrame / activity projection
  ↓
xtrm-app
  ├─ Frame navigation
  ├─ selected-Frame conversation view
  ├─ zoomed-out Frame cards
  └─ branch/fork tree
```

Provider transcript/session state remains authoritative. The app owns
presentation metadata and projections, not another agent runtime or durable work
store.

## Current assets

The package contains design docs, the executable Console v2 shell (`src/`), a
historical static prototype (`prototype/`), and starter runtime/provider
abstractions in `host/` (Frame projector and provider adapter sketches, outside the WebView bundle, not yet wired). Read
[`docs/README.md`](docs/README.md) before implementation work.

### Agent half (PRD §36)

The rail's `Console` / `Agent` switch (`Ctrl .`) opens the Agent half at `/agent`:
session sidebar, Frame surface, `@` reference picker, and the four tool classes. It runs on the
typed agent fixture (`src/adapters/agent/fixture.ts`) unless `VITE_XTRM_AGENT=live`. Review
screenshots are regenerated by `npx playwright test e2e/screens.spec.ts` into
`docs/screenshots/agent-half/`.

**Live agent host (XTRM-572, read path).** With `VITE_XTRM_AGENT=live` the Agent half reads an
XTRM agent host (`xtrm.agent-host-api.v1`) through the dev bridge: the SSH-forwarded host while the
`Host` connection is up, else the loopback host on this machine (`XTRM_AGENT_HOST_PORT`, or the port
in `~/.xtrm/run/agent-host.json` written by `xt host start`). Sessions come from `GET /v1/sessions`
and `/v1/sessions/:id`; Frames and tool activity are projected in the app
(`src/adapters/agent/projector.ts`) from the host event stream (`xtrm.agent-event.v1`), read with
`fetch` streaming and resumed with `Last-Event-ID` (never `EventSource`). A Frame opens on
`before_agent_start` (or `agent_start` for Claude hooks, which report no prompt text) and closes only
on `agent_settled`. Tool class and MCP server come from the host's `origin`; calls with
`parentToolCallId` render inside their parent, and the built-in `codemode` tool renders as a script
block with its nested calls. Claude sessions are presence only; stopped sessions are history only. The wire types are mirrored in `src/adapters/agent/protocol.ts`
from `@xtrm/contracts` (core v0.14.0).

**Session history (XTRM-604, PRD §26, §36.11 criterion 28).** The host's replay buffer holds 1024
events, so the stream alone misses older Frames. For a Pi session, live or history only, the adapter
reads `GET /v1/sessions/:id/history` (core XTRM-604, through the bridge's
`/xtrm-api/agent-host/api/v1/sessions/:id/history`): the journal's `message` and `compaction` entries on
the active branch, read only. `src/adapters/agent/history.ts` projects them through the same
projector as live events and merges the two lists. A live Frame matches a journal Frame that has one
of its user-message timestamps, or one of its tool call ids (a Frame cut by the buffer). Each Frame is
shown once, numbered from 1, and the live Frame wins: origins, nested calls, prompts and status. The
history is read again after a stream reconnect and once a session stops. Calls known only from the
journal carry no host origin and show as unclassified (extension) calls, with no nested calls. A Frame
only from the journal shows `terminal` ingress. A host without the route, or a Claude session, shows
the stream's Frames only.

**Live write path (XTRM-597).** The composer posts an `xtrm.agent-host-api.v1` `submit_request` to the
bridge (`POST /xtrm-api/agent-host/api/v1/submit`: loopback, same-origin, `application/json` only),
which forwards it to the host's `POST /v1/submit`. The command is `xtrm.agent-command.v1`: `prompt`
while the session is idle, `steer` or `follow_up` (the composer's delivery switch) while it works,
`abort` from Stop, and `extension_ui_response` for an extension request. The host serializes submits
per session (PRD §35.8 item 5): a normal prompt that reaches a working session, for example from a
second app client that has not seen the update yet, is answered `busy`, and the composer then offers
`Send as steer` and `Send as follow-up` for the same text. Nothing is queued or retried by the app.
An `extension_ui_request` (`confirm`, `select`, `input`) renders inline in the running Frame;
`extension_ui_resolved` closes the block whoever answered, and the block says whether it was answered
here or in the terminal. A delivered steer or follow-up appears in the Frame as
`Delivered while working: …`. The Frame header shows its ingress, `GUI` or `terminal`.

**Live `@` references (XTRM-598, PRD §36.6, §36.12 item 2).** Every reference resolves when the
composer submits, through its own adapter: `@issue` and `@epic` through `adapters/substrate`
(revision `rev:<n>`, contract sections in order up to 16 KB, then `sb issue show <ref>`), `@gh-issue`
and `@pr` through `adapters/github` (revision `updated:<time>`, 8 KB, a PR diff always by pointer),
and `@file`, `@commit`, `@session`, `@agent`, `@frame` on the agent host (`POST
/xtrm-api/agent-host/api/v1/references/resolve` → the host's `POST /v1/references/resolve`, against
the session's cwd and registry: `sha256:` file revisions, `../` escapes rejected). A reference above
its kind's budget is an excerpt plus a pointer. An unresolved reference, or more than 96 KB in total,
blocks submit with the reason and marks the chip. The resolved references travel in
`submit_request.references`; the host forwards only the command to the session, so the app also
appends them to the message as a context block (`src/adapters/agent/references.ts`: an index with
one JSON line per reference, then each reference's content). The Frame shows the operator's text and
keeps each reference with the revision it was given; an excerpt is marked on its chip. In the picker,
host kinds have no search route: a typed `@file:<path>` or `@commit:<sha>` is offered once it
resolves, and `@session` lists the host's sessions. `@epic`, `@agent` and `@frame` are typed only.

**Model, thinking level, context and repository (XTRM-609, PRD §36.3, §36.11 criterion 5).** Model
(`<provider>/<model id>`), thinking level and context utilization come from the host: the latest
`session_status` frame on the event stream (`xtrm.agent-event.v1`, core XTRM-603), else the host session
summary, else the last assistant message for producers that send no status. Each `session_status`
replaces the previous state; a context whose tokens Pi cannot estimate (after compaction) shows no
meter. A history-only session shows only what the host summary reports. Rows show the model id and
thinking level (`deepseek-v4.1-flash · high`) and the meter; details show the full model and
`1% · 7k / 1000k`. Sessions group by the host's `repository` (`owner/name` from the git remote, for
live and history-only sessions alike, core XTRM-608); only without it does the bridge resolve a local
`repositoryPath` (else the worktree or cwd) to `owner/name`, and only for a loopback host. The drawer's
session panel shows the repository and its root.

**Direct mode (XTRM-600, PRD §35.5).** For a host reached through an HTTPS front (`tailscale serve`
in front of a host started with `xt host start --direct --direct-host <front name>`), the `Host`
panel has a `Direct` mode: the front URL (`https://…`; `http://` only on `127.0.0.1` / `localhost`),
a one-time pairing token from `xt host pair` on that host, and a device name. The bridge
(`server/agent-host-direct.ts`) exchanges the token once at `POST /v1/pair`
(`xtrm.agent-host-auth.v1`, mirrored in `src/adapters/agent/host-auth.ts`) and keeps the device token
in its own file (`XTRM_AGENT_DEVICE_FILE`, mode `0600`, directory `0700`); the page sees only the
device summary. While no SSH connection is up, the read routes, the event stream (fetch streaming,
same origin as the page) and the write routes go to the front with `Authorization: Bearer`. When the
front answers 401 (for example after `xt host revoke <id>`), the bridge deletes the token and the
panel shows a re-pair prompt. Host selection order: SSH forward, then the paired front, then the
loopback host.

`npm run test:e2e:real-host` runs the live Agent half against a real host: an isolated `xt host start`
(temp `HOME`, `--socket`, `--port`, `--direct`), a real Pi session with the `xtrm-agent-host` extension in a
private tmux server, a prompt typed in its terminal, and the real Claude hook reporter. Its write-path
spec (`e2e/real-host/write-path.spec.ts`) drives a second Pi session that also loads a test extension
with one confirm tool (`e2e/real-host/probe-extension.ts`): a GUI prompt, busy and Steer from a second
app client, Stop, and the confirm answered once in the GUI and once in the terminal. Its references
spec (`e2e/real-host/references.spec.ts`) resolves `@file` with a line range, `@issue` (against the real
Substrate board, read only: `XTRM_SUBSTRATE_WRITES=0`) and `@session` of a second live Pi session,
sends an oversize file as an excerpt, and checks that a `../` escape blocks submit. Its session status
spec (`e2e/real-host/session-status.spec.ts`, XTRM-609) runs Pi in a repository with an origin remote and
checks the row's model and thinking level, the meter after a turn, a thinking change from the terminal,
and the owner/name group live and after `/quit`. Its session history spec (`e2e/real-host/session-history.spec.ts`, XTRM-604) drives
turns until the host's replay buffer has dropped the session's first Frames, then checks that the Frame
dock shows every Frame once, in order, live and after `/quit`.
`npm run test:e2e:real-host:direct` (`e2e/real-host/direct-mode.spec.ts`, XTRM-600) runs the same host
behind a local front that adds `X-Forwarded-For` and has the bridge reach it only through that front:
pairing succeeds once, a replay fails, the session list and a streamed Frame work with the device
token, and `xt host revoke` shows the re-pair prompt; the device file lives in a temp dir removed on
teardown. The host and the extension must come from the same core
commit: set `XTRM_REAL_HOST_XT=<core>/cli/dist/index.cjs` with `XTRM_CORE_DIR=<core>` to run a host built
from that checkout instead of the installed `xt` (an older host rejects newer frames). It needs `xt`
0.14.0+, `pi` 1.0.0, tmux, the `xtrm-dev/core` checkout (`XTRM_CORE_DIR`, default `~/dev/core`) and an
`opencode-go` entry in `~/.pi/agent/auth.json` (only that entry is copied into the temp agent dir,
deleted on teardown). The run log goes to `.receipts/real-host/`, screenshots to
`docs/screenshots/agent-half/real-host/`.

**Agent host over SSH (PRD §35.5, §35.8 item 2; XTRM-585).** The `Host` control in the
session sidebar header holds one SSH connection: a target (`user@host` or a `~/.ssh/config`
alias) and an optional remote command. Connect runs, with the operator's own `ssh` and agent
(`BatchMode=yes`, stdin closed, timeout), `"${SHELL:-/bin/sh}" -lc 'xt host ensure --json'`; on
exit 127 the same with `-ilc`; then the stored remote command. It takes the last stdout line
that parses as `xtrm.agent-host-ensure.v1`, rejects a different protocol major (the message names
`xt update`), and holds `ssh -N -L 127.0.0.1:<local>:127.0.0.1:<port> <target>` until Disconnect
or dev-server exit. The remote host keeps running. The bridge (`server/agent-host-ssh.ts`) reads
the host API through that port and answers loopback clients only. Open in terminal (session
header) builds `ssh -t <target> tmux attach -t <session>`, copies it, and starts it when
`XTRM_TERMINAL` names a terminal (for example `foot` or `kitty --`).

| variable | meaning |
|---|---|
| `VITE_XTRM_AGENT` | `fixture` (default) or `live` (sessions, Frames and tool activity from the agent host) |
| `VITE_XTRM_AGENT_HOST` | `live` (default, the bridge) or `fixture` (every connection state, no ssh) |
| `XTRM_AGENT_HOST_PORT` | loopback agent host port for the live read path when no SSH connection is up (default: the port in `~/.xtrm/run/agent-host.json`) |
| `XTRM_SSH_BIN` | ssh executable (default `ssh` on PATH) |
| `XTRM_AGENT_CONNECTION_FILE` | connection settings (default `~/.xtrm/app/agent-host-connection.json`, mode `0600`); `~/.ssh` is never read or written |
| `XTRM_AGENT_DEVICE_FILE` | direct-mode front URL, device and device token (default `~/.xtrm/app/agent-host-device.json`, mode `0600`) |
| `XTRM_TERMINAL` | optional terminal launcher for Open in terminal |
| `XTRM_CORE_CLI` | test only: core `cli/dist/index.cjs` for `server/agent-host-ssh.integration.test.ts` (fake `ssh`, local run; skipped when absent) |

### Research runs: seeing published runs locally

The Research surfaces read published runs through the `xtrm-research` CLI, not
through the repository. The supported launch resolves the runtime identity for
*this* checkout instead of exporting paths by hand. Four settings decide what
you see:

| variable | what it points at |
|---|---|
| `VITE_XTRM_RESEARCH` | `live` (default) or `fixture`; `fixture` serves the captured UI fixture and needs no CLI |
| `XTRM_RESEARCH_BIN` | the release-matched `xtrm-research` executable |
| `XTRM_RESEARCH_ROOT` | the published runs root |
| `XTRM_RESEARCH_REGISTRY_ROOT` | the matching shipped registry |

**Install (once per checkout).** The launcher expects the CLI at
`packages/research/.venv/bin/xtrm-research`:

```bash
cd packages/research
python3 -m venv .venv
./.venv/bin/pip install -e '.[dev]'
```

**Update (after pulling changes to `packages/research`).** The install is
editable, so source edits are picked up immediately; rerun the install when the
entry point, dependencies, or `pyproject.toml` change:

```bash
cd packages/research && ./.venv/bin/pip install -e '.[dev]'
```

**Launch:**

```bash
npm run research:dev                     # resolve all four, print identities, then start Vite
npm run research:dev -- --port 5180      # other flags go to Vite
npm run research:dev -- --runs DIR       # a different runs root
npm run research:fixture                 # UI only, no runs root needed
```

`research:dev` prints the UI commit, the resolved CLI path / version / source
commit and both roots, then starts Vite. It **refuses to start** when the
resolved CLI belongs to a different checkout than the app (the ambient-symlink
trap) or when it lacks a read verb the bridge calls, naming the two checkouts or
the missing verbs. At runtime the bridge has no PATH fallback: an unset
`XTRM_RESEARCH_BIN` or `XTRM_RESEARCH_REGISTRY_ROOT` is a `503` naming the
missing variable, never a silent read of another worktree. The registry root
matters just as much — without it the run page cannot resolve a run's
Experiment / Workload / QuestionSpec definitions, and the semantic sections come
back empty.

Then open `/research/runs` and pick a run. The run page resolves the exact
versioned definitions the run's manifest references and shows why the run
exists, what would have counted, the structured result, the method (each System
One question with its actual primitive type — `noul` / `choice` / `score` — and
its `criteria.true|false`), and every metric with its glossary meaning and
direction.

**Runs and datasets are not in git, by design.** They hold private board text
(every sample's input carries the contract it was run on) and a multi-hundred-
MB snapshot; they live under `~/.xtrm/research/` (mode 700) and the original run
directory is the evidence of record. To hand a run to someone else, make a
sanitized reading copy instead of exporting raw:

```bash
npm run research:snapshot -- --out ~/.xtrm/research/shared/board-v2 \
  --run planning-ready-v2-atomic-explicit --run planning-ready-v2-holistic
npm run research:dev -- --runs ~/.xtrm/research/shared/board-v2
```

`research:snapshot` redacts every string value in every copied file with
`xtrm_research.guards.redact` — the same rule that decides what may be sent to a
model — keeps structure, keys and numbers intact so the copy is still readable
by the CLI and by the app, writes an `index.json` with headline metrics and file
hashes, and fails closed if any text would still be redacted. Definitions and
reports are the parts that belong in review: they live in
git (`packages/research/registry`, `packages/research/docs`).

Layout:

```text

                 SidebarSection/Row, Drawer, InspectorSection, CommandMenu, ResizablePanel, …)
```

## GitHub App sign-in (operators)

Attributed GitHub actions need a per-user login, not the shared workspace
credential. Console v2 signs in through the **xtrm-console GitHub App**
(owner: the `xtrm-dev` org, installable on any account) using the OAuth device
flow against the App's `client_id`: the app shows a code, the operator enters
it at `github.com/login/device`, and the backend polls GitHub itself until the
flow completes. The browser never receives or stores tokens and xtrm-app never
calls `api.github.com` directly.

1. **Install the app.** Open Settings → GitHub in Console v2 (or go to
   `https://github.com/apps/xtrm-console/installations/new`) and install
   xtrm-console on the accounts whose repositories you work in. Per-installation
   repository access and fine-grained permissions (Pull requests, Issues,
   Contents, Checks, Actions, Metadata read) keep the grant least-privilege;
   user tokens expire (default 8 h) and the backend refreshes them.
2. **Configure the backend (XTRM-404).** The Console backend holds the App's
   `client_id`, authenticates the device flow, and keeps user tokens in the
host OS keychain (or a file store where no keychain exists). See the backend
   issue (XTRM-404) for the exact environment variables and secret handling —
   never paste App secrets or user tokens into xtrm-app source, `.env` files
   checked into git, or chat logs.
3. **Sign in.** Top bar → Sign in with GitHub, or Settings → GitHub →
   Sign in. Until the backend lands, the live adapter degrades to
   `not_configured`; reads fall back to the shared `GITHUB_TOKEN` /
   `gh auth token` credential (read-only) or fail closed with an inline
   notice that links Settings.

Auth states surfaced inline (top bar, Settings → GitHub, Pull requests and
repo views): `not_configured`, `signed_out` (read-only via shared token, or
sign-in required), `pending` (device code), `signed_in`, `expired`, `error`,
plus a per-repository Install callout when the app is missing there.
For local UI work without a backend, `VITE_XTRM_GITHUB=fixture` serves a
controllable fixture covering every state (`createFixtureGithubAuth`).

Known limits: list readiness is known only for dispatchable issues (XTRM-393);
the Substrate bridge exists only in the Vite dev/preview server. The retired
cross-repository programme adapter was deleted with its surface (ADR-002 §12 R2);
Project reads its own typed adapters as they land (XTRM-813/815).

Screenshots: `docs/screenshots/console-v2-shell/`. Regenerate with
`PLAYWRIGHT_CORE=<playwright-core dir> node scripts/screenshots.mjs .receipts dark`.

Current direction is Linux-first, Tauri 2 + React/TypeScript unless packaging
evidence rejects it, with direct Pi `AgentSessionRuntime` as the first vertical
and a Claude adapter after the Pi path is proven.
