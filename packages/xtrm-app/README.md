# xtrm-app

Linux-first desktop application workspace for XTRM's human ↔ agent interface.

**Status:** design/starter implementation, not a build-complete desktop app. The
canonical design is `docs/xtrm-gui-prd.md`; the current interaction unit is
**Frame** (`InteractionFrame`). This package is also the implementation root for
**XTRM Console v2** (PRD §34); start from [`docs/README.md`](docs/README.md).

## Product boundary

```text
human input
  ↓
provider session (Pi first, Claude adapter later)
  ↓
InteractionFrame / activity projection
  ↓
xtrm-app
  ├─ Frame navigation
  ├─ selected-Frame conversation view
  ├─ zoomed-out Frame cards
  └─ branch/fork tree
```

Provider transcript/session state remains authoritative. The app owns
presentation metadata and projections, not another agent runtime or durable work
store.

## Current assets

The package contains design docs, the executable Console v2 shell (`src/`), a
historical static prototype (`prototype/`), and starter runtime/provider
abstractions in `host/` (Frame projector and provider adapter sketches, outside the WebView bundle, not yet wired). Read
[`docs/README.md`](docs/README.md) before implementation work.

### Agent half (PRD §36)

The rail's `Console` / `Agent` switch (`Ctrl .`) opens the Agent half at `/agent`:
session sidebar, Frame surface, `@` reference picker, and the four tool classes. It runs
on the typed agent fixture (`src/adapters/agent/fixture.ts`) until the agent host exists;
XTRM-572 adds the live adapter. Review screenshots are regenerated by
`npx playwright test e2e/screens.spec.ts` into `docs/screenshots/agent-half/`.

### Research runs: seeing published runs locally

The Research surfaces read published runs through the `xtrm-research` CLI, not
through the repository. The supported launch resolves the runtime identity for
*this* checkout instead of exporting paths by hand. Four settings decide what
you see:

| variable | what it points at |
|---|---|
| `VITE_XTRM_RESEARCH` | `live` (default) or `fixture`; `fixture` serves the captured UI fixture and needs no CLI |
| `XTRM_RESEARCH_BIN` | the release-matched `xtrm-research` executable |
| `XTRM_RESEARCH_ROOT` | the published runs root |
| `XTRM_RESEARCH_REGISTRY_ROOT` | the matching shipped registry |

**Install (once per checkout).** The launcher expects the CLI at
`packages/research/.venv/bin/xtrm-research`:

```bash
cd packages/research
python3 -m venv .venv
./.venv/bin/pip install -e '.[dev]'
```

**Update (after pulling changes to `packages/research`).** The install is
editable, so source edits are picked up immediately; rerun the install when the
entry point, dependencies, or `pyproject.toml` change:

```bash
cd packages/research && ./.venv/bin/pip install -e '.[dev]'
```

**Launch:**

```bash
npm run research:dev                     # resolve all four, print identities, then start Vite
npm run research:dev -- --port 5180      # other flags go to Vite
npm run research:dev -- --runs DIR       # a different runs root
npm run research:fixture                 # UI only, no runs root needed
```

`research:dev` prints the UI commit, the resolved CLI path / version / source
commit and both roots, then starts Vite. It **refuses to start** when the
resolved CLI belongs to a different checkout than the app (the ambient-symlink
trap) or when it lacks a read verb the bridge calls, naming the two checkouts or
the missing verbs. At runtime the bridge has no PATH fallback: an unset
`XTRM_RESEARCH_BIN` or `XTRM_RESEARCH_REGISTRY_ROOT` is a `503` naming the
missing variable, never a silent read of another worktree. The registry root
matters just as much — without it the run page cannot resolve a run's
Experiment / Workload / QuestionSpec definitions, and the semantic sections come
back empty.

Then open `/research/runs` and pick a run. The run page resolves the exact
versioned definitions the run's manifest references and shows why the run
exists, what would have counted, the structured result, the method (each System
One question with its actual primitive type — `noul` / `choice` / `score` — and
its `criteria.true|false`), and every metric with its glossary meaning and
direction.

**Runs and datasets are not in git, by design.** They hold private board text
(every sample's input carries the contract it was run on) and a multi-hundred-
MB snapshot; they live under `~/.xtrm/research/` (mode 700) and the original run
directory is the evidence of record. To hand a run to someone else, make a
sanitized reading copy instead of exporting raw:

```bash
npm run research:snapshot -- --out ~/.xtrm/research/shared/board-v2 \
  --run planning-ready-v2-atomic-explicit --run planning-ready-v2-holistic
npm run research:dev -- --runs ~/.xtrm/research/shared/board-v2
```

`research:snapshot` redacts every string value in every copied file with
`xtrm_research.guards.redact` — the same rule that decides what may be sent to a
model — keeps structure, keys and numbers intact so the copy is still readable
by the CLI and by the app, writes an `index.json` with headline metrics and file
hashes, and fails closed if any text would still be redacted. Definitions and
reports are the parts that belong in review: they live in
git (`packages/research/registry`, `packages/research/docs`).

Data sources (select with `VITE_XTRM_GITHUB|SUBSTRATE|PROGRAM|RESEARCH=live|fixture`):

| surface | default | source |
|---|---|---|
| GitHub / repository Activity, repository list | live | Console v1 backend (`XTRM_CONSOLE_URL`, default `http://127.0.0.1:3030`) via Vite proxy |
| Substrate Issues list, issue page, issue drawer, Jira-style editing | live | installed `sb` CLI envelope `substrate-cli/v1` through an allow-listed bridge; reads plus writes via `sb issue edit/state/note/create` (`XTRM_SUBSTRATE_WRITES=0` for read-only, `XTRM_SB_DB=<path>` for a dev database); never SQLite |
| Research runs, registry experiments, sample records, metrics, comparison | live | `xtrm-research --json` read verbs (`xtrm-research-cli/v1`) through an allow-listed bridge, pointed by `XTRM_RESEARCH_BIN`, `XTRM_RESEARCH_ROOT`, `XTRM_RESEARCH_REGISTRY_ROOT`; start it with `npm run research:dev` (below) or `npm run research:fixture` for the UI alone |
| Program | fixture | Console backend `/api/programme` is disabled by deployment policy (404); fixture uses the same `ProgrammeSnapshotResponse` mapper |

## GitHub App sign-in (operators)

Attributed GitHub actions need a per-user login, not the shared workspace
credential. Console v2 signs in through the **xtrm-console GitHub App**
(owner: the `xtrm-dev` org, installable on any account) using the OAuth device
flow against the App's `client_id`: the app shows a code, the operator enters
it at `github.com/login/device`, and the backend polls GitHub itself until the
flow completes. The browser never receives or stores tokens and xtrm-app never
calls `api.github.com` directly.

1. **Install the app.** Open Settings → GitHub in Console v2 (or go to
   `https://github.com/apps/xtrm-console/installations/new`) and install
   xtrm-console on the accounts whose repositories you work in. Per-installation
   repository access and fine-grained permissions (Pull requests, Issues,
   Contents, Checks, Actions, Metadata read) keep the grant least-privilege;
   user tokens expire (default 8 h) and the backend refreshes them.
2. **Configure the backend (XTRM-404).** The Console backend holds the App's
   `client_id`, authenticates the device flow, and keeps user tokens in the
host OS keychain (or a file store where no keychain exists). See the backend
   issue (XTRM-404) for the exact environment variables and secret handling —
   never paste App secrets or user tokens into xtrm-app source, `.env` files
   checked into git, or chat logs.
3. **Sign in.** Top bar → Sign in with GitHub, or Settings → GitHub →
   Sign in. Until the backend lands, the live adapter degrades to
   `not_configured`; reads fall back to the shared `GITHUB_TOKEN` /
   `gh auth token` credential (read-only) or fail closed with an inline
   notice that links Settings.

Auth states surfaced inline (top bar, Settings → GitHub, Pull requests and
repo views): `not_configured`, `signed_out` (read-only via shared token, or
sign-in required), `pending` (device code), `signed_in`, `expired`, `error`,
plus a per-repository Install callout when the app is missing there.
For local UI work without a backend, `VITE_XTRM_GITHUB=fixture` serves a
controllable fixture covering every state (`createFixtureGithubAuth`).

Known limits: list readiness is known only for dispatchable issues (XTRM-393);
the Substrate bridge exists only in the Vite dev/preview server; Program has no
typed reference to Substrate issues in snapshot v3 (the fixture's
`metadata.executable_refs` is a proposed field).

Screenshots: `docs/screenshots/console-v2-shell/`. Regenerate with
`PLAYWRIGHT_CORE=<playwright-core dir> node scripts/screenshots.mjs .receipts dark`.

Current direction is Linux-first, Tauri 2 + React/TypeScript unless packaging
evidence rejects it, with direct Pi `AgentSessionRuntime` as the first vertical
and a Claude adapter after the Pi path is proven.
