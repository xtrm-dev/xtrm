The Console UI system: one rail, quiet toolbars, small rows, PR identity, Project visuals, one Factory drawer

The operator's review of 2026-11-18 asked for a coherent UI system before more surfaces land. This page shows the six answers in the Console's own tokens, in light and dark. The committed spec packages/xtrm-app/docs/design/console-ui-system.md names every token and component, with file, props and consuming surfaces.

Reading the page. The page chrome follows the Mercury style (light grey page, white cards). Each “Console” frame inside a card is a faithful miniature of the app, rendered with the token values of src/styles.css in the light theme and in the dark theme. Restraint (binding for every slice, operator 2026-11-18). The app must not become too colourful or fill the viewport with pills. T1 · Chips: solid colour, pure white ink

src/ui/badge.tsx · src/styles.css

The change: the chip stops being a dim tint with muted ink. The chip becomes the colour, the ink becomes pure white, and the shape becomes a pill. One solid tone set serves both themes, so a status never changes meaning between light and dark.

Same tone set in both themes: --chip-accent #5b54ea, --chip-att #b45309, --chip-success #157f4d, --chip-danger #c0392b, --chip-neutral #6b6b76. Pure white on each tone measures 5.38, 5.02, 5.03, 5.44 and 5.26 to 1, so every chip clears 4.5:1 without a per-theme ink swap. Each tone also clears 3.3:1 against the dark surface, so the chip keeps a visible edge in dark mode.

statussolid tonewhy this tone
Readyaccentthe product accent means “dispatchable”, matching the accent used for “Start work”
In progressattention, amberamber is the only tone that reads as “live now” without reading as a warning
Blockeddangerunchanged meaning, now filled instead of tinted
Done, Attestedsuccessunchanged meaning, now filled
Draft, Deferred, Staleneutrala desaturated slate keeps three “not active” states quiet without hiding them
Rejecteddangershares the danger tone with Blocked; the word separates them
What this costs. A solid chip is louder than a tint, so the list now has colour at every row. That is the request, but it means only one saturated chip may appear per row — the status. Everything else stays neutral, which is why the key chip and the rollup pills are tinted, not filled.

T2 · Issue keys get a tinted chip

src/ui/sidebar.tsx · list rows

The change: XTRM-933 stops being bare mono text. It gets a chip with a 13 % accent tint (22 % in dark) and accent ink, so the key is a stable anchor the eye can find without reading, and the title still carries the weight.

Tinted chip ink measures 6.50:1 light and 7.77:1 dark against its own chip, and the chip itself stays quiet against the surface, so it never competes with the status chip beside it. The same chip serves nested keys and PR refs.

One question first. A key chip on every row adds a second coloured object per row. The alternative is to tint only the prefix shortlist, or to tint keys in the sidebar and the drawer but leave list keys plain. This is O6 below.

T5 · The treated single-line list

issues list, one-line variant · everything at once

What it shows: the one-line row from L3b, at 36 px with a 14 px title, with a tinted key chip, a solid status chip, and round pills behind the three rollup counts. The pills replace the bare glyph and number.

The rollup pills use a 12 % tint of their own tone so the count and its glyph read as one object: layers for children, activity for events, outbound for pointers. The PR ref stays neutral. The age stays faint and tabular.

Pills are optional per column. Children, events and pointers each gain a pill; the PR ref and the age do not, because a pill around a key would compete with the key chip and a pill around a relative time would be noise. If a row carries only one count, drop the pill and keep the bare glyph.

Order on line 1. State chip, then title, then age at the right edge. The state is a word, so it reads before the title and the eye can skip whole groups by colour. Line 2 keeps author, diff, checks, review, comments and the issue key, in that order.

P2 · Which pill

same row, six candidates, each shown at rest and hovered

The question: the pill has to be visible at rest — the operator's complaint is that the key had no background at all — but it must not compete with the solid status chip that usually sits beside it. Six candidates, at rest and on hover:

F5 soft accent border — the operator's idea — marks the key as Substrate's own without spending a fill: the rule is the accent at 40 % light, and hovering lifts it to 58 % with an accent wash. what I would build unless told otherwise

Side by side: the list keeps its key; the places that link to an issue get the pill. Left: unchanged list rows. Right: the three link surfaces.

Recommended: F5 with L1 — IssueKeyPill draws the locator in text-accent-ink and the slim ref in a pill: inline-flex h-5 items-center gap-1 rounded-md border border-accent/35 bg-transparent px-1.5 font-mono text-xs, the border stepping to accent/55 with an accent-soft wash on hover and focus. It needs no new colour token — --x-accent already exists and the opacity does the softening — and it gives Substrate keys a signature that no other key in the app shares: PR keys are state-coloured text, Jira keys are bordered and external, and this one is violet and internal. Where the locator equals the ref (a root issue), only the pill is drawn, so the row never shows the same string twice. F1 remains the quiet fallback if the accent reads as too much colour in the drawer.
