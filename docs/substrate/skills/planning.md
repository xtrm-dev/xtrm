# Planning (normative migration reference: Substrate-native doctrine)

Planning authors executable authority. It produces Issue revisions another
worker can execute without previous chat history — not a large plan document.

## The pipeline

```text
conversation / operator request
        ↓
PlanDraft
        ↓
seven-field contracts
        ↓
ownership / context
        ↓
hierarchy / dependencies
        ↓
overlap analysis
        ↓
sb plan check
        ↓
sb plan apply
        ↓
readiness
```

## Steps

1. **Ground first.** For non-draft work, verify repository, runtime, and board
   state before structuring: recent commits and PRs, `sb issue list|ready`,
   current CLI help. Name real ownership and validation; do not run an
   archaeology ritual.
2. **Draft the smallest sufficient structure.** Idea for later → draft capture
   only. One bounded task → one contract. Feature or PRD → decompose by
   ownership and ship boundary, wire dependencies. Messy board → triage.
   Proof-heavy work → test/telemetry planning. High-cost or ambiguous design →
   premortem before dispatch. Never create an epic because planning feels
   incomplete without one.
3. **Write seven-field contracts.** Each Issue carries PROBLEM, SUCCESS,
   SCOPE, NON_GOALS, CONSTRAINTS, VALIDATION, OUTPUT, plus SCRUTINY,
   ownership, and context refs. Prescribe what must be true, not the
   implementation mechanism — unless the mechanism is itself a constraint.
4. **Wire ownership, hierarchy, overlap.** Set ownership and context refs so
   workers do not collide; parent/child links for decomposition; typed graph
   edges after creation (`sb issue relate --from <a> --to <b> --kind
   blocks|relates_to|discovered_from|supersedes|duplicates`). Overlaps between
   planned Issues are reported advisory at check time — resolve real
   collisions before apply.
5. **Check, then apply.** `sb plan check --file plan.json` validates the whole
   draft up front (cycles, alias collisions, invalid refs; refuses to apply on
   failure). `sb plan apply --file plan.json` executes it atomically under one
   idempotency key (`planKey`: same key plus same content reapplied is a
   no-op). Never hand-execute a plan the checker rejects.
6. **Attest readiness.** New or revised Issues are not executable until
   attested: `sb issue validate <ref>` reports structural validity,
   attestation currency, and blockers; `sb issue attest <ref> --outcome ready
   --policy <p> --attested-by <who>` records the attestation. Draft work that
   still needs semantic attestation must not be dispatched.

## Repair during execution (the planning loop)

Planning is also how an insufficient or changed Issue is repaired mid-flight:

```text
execution pauses
    ↓
/planning (revise the contract)
    ↓
Issue revision (execution-bearing edit invalidates old readiness)
    ↓
new readiness attestation
    ↓
execution resumes
```

Trigger on any SCOPE, SUCCESS, NON_GOALS, CONSTRAINTS, VALIDATION, OUTPUT,
ownership, context, or scrutiny change. Never patch missing scope into a
dispatch prompt, a channel message, a handoff note, or a Specialist
instruction and continue as if authorization had not changed.

## Continuity while planning (by reference; doctrine lives in using-xtrm)

Planning sessions are execution too: append findings, decisions, and
blockers with `sb issue note <ref> … --kind …`, checkpoint before
`sb plan apply`, and resume a planning Issue with `sb issue resume` plus
`sb journal since`. Journal entries never carry authority (Journal != Issue)
and never become reusable truth on their own (Journal != Memory). The plan
check report and the apply result, together with readiness attestations, are
the planning provenance — recorded, not summarized away.

## Handoff and close of planning work

A finished plan hands off like any work: the created or revised Issues stay
the executable authority; a bounded Journal handoff entry records the plan
key, created refs, attestation state, blockers, and pending work; the next
worker restarts from `sb issue resume`. When the planning Issue itself is
done, validate, checkpoint, `sb issue close <ref>`, and `sb issue release
<ref> --holder <who>`.

## Edit classification (mechanical)

- Metadata — `sb issue edit <ref> --title … --priority …`: no revision, no
  readiness change.
- Execution-bearing — `sb issue edit <ref> --contract … --ownership …
  --context-refs … --scrutiny …` (guard races with `--expected-revision N`):
  new revision, readiness invalidated, re-attest before dispatch.
- Graph — `sb issue relate / unrelate --from <a> --to <b> --kind …`: typed
  relation change, never a contract edit; reparenting preserves machine ID
and durable human ref.

A reviewer finding that changes authorized requirements is a planning cycle,
not a comment edit: the contract moves, readiness resets, execution resumes
only after re-attestation.
