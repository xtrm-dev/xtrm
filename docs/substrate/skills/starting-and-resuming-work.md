# Starting and Resuming Work (normative migration reference: Substrate-native doctrine)

Continuity is part of execution. A session ending is normal; work disappearing
with it is a failure. A fresh worker reaches the executable state from durable
sources alone — without previous chat history.

## The model (old → new)

Retired:

```text
bd prime → bd ready → bd show → bead notes → conversation reconstruction
```

Canonical:

```text
resolve Issue
        ↓
sb issue show
        ↓
read exact revision / readiness
        ↓
claim if needed
        ↓
sb issue resume
        ↓
Resume Capsule
        ↓
read only Journal delta / evidence needed
        ↓
continue
```

## Cold start or takeover

1. Identify the repository, worktree, and branch.
2. `sb issue show <ref>` — read the exact Issue revision, its readiness
   (`sb issue validate <ref>`), and current claim state. A draft, stale, or
   contradicted Issue is repaired through `/planning` before any other step.
3. Claim if unowned: `sb issue claim <ref> --holder <who>`. If another live
   session holds the claim, resolve ownership before creating another worker —
   duplicate agents on one task are a race unless explicitly coordinated.
4. `sb issue resume <ref>` — render the Resume Capsule. It carries the current
   revision, latest durable checkpoint, journal delta cursor, claim, blockers,
   child Issue status, pending asks, and provenance state. The capsule is a
   bounded continuation projection: derived, never a source of truth.
5. Read only what the capsule points at: `sb journal since <ref> <cursor>` for
   entries after the checkpoint, plus cited evidence. Never dump the full
   history, never reconstruct from chat, never trust an inherited summary over
   live state — compare and correct stale claims first.
6. Continue from the capsule. Journal the takeover boundary
   (`sb issue note <ref> … --kind handoff`, or a checkpoint) so the next
   worker sees one clean seam, not two half-overlapping narratives. Journal
   entries are continuity, never reusable truth on their own
   (Journal != Memory — see using-xtrm). When resumed work completes,
   validate, checkpoint, close (`sb issue state <ref> done` or `sb issue
   close <ref>`), and release the claim
   (`sb issue release <ref> --holder <who>`).

## Ownership map before edits

Before editing or dispatching, know for each item: work item → current owner
→ workspace/branch → expected output → blocker/reply state. Ambiguous
ownership resolves before new workers exist.

## Context pressure and handoff

Treat context capacity as an execution resource. When remaining context no
longer covers the next coherent phase, stop starting new large work and hand
off early: the Issue stays the executable authority; a bounded Journal
handoff/checkpoint entry carries blockers, known pending work, and provenance
refs; the next worker restarts from `sb issue resume`. Long transcripts do
not belong in the Journal.

Before compaction or exit, write the mechanical checkpoint first
(`sb journal checkpoint <ref>`) — durable even if everything after fails —
then continue from the capsule. If a summary ever disagrees with Issue,
Journal, or provenance state, durable Substrate state wins.

## What this skill does not own

Contract authoring and repair belong to `/planning` (G8: authority change →
stop → revise → re-attest → resume). The full authority stack, worker loop,
journal kinds, and classification rules belong to `using-xtrm`. This skill
owns one motion only: from nothing (or a failing context) to positioned,
claimed, capsule-restored, delta-read continuation.
