# Coordinator (canonical Substrate-native doctrine)

The coordinator owns programme continuity across child Issues. The coordinator
Journal represents programme continuity, not child transcript aggregation. A
fresh coordinator reaches the executable state from Issue revision plus capsule
plus journal delta alone, without previous chat history.

## Initialization (ADR §72)

If Substrate reports this repository is uninitialized: run `sb init`.

```text
sb init
```

Never guess the only project, invent a project id, or manually create/link
during normal work. One Git repository maps to exactly one Project. Contract
changes use only `sb issue edit` and `sb plan apply`; progress uses the
Journal.

## Authority the coordinator obeys

The executable contract is a ready Issue revision: PROBLEM, SUCCESS, SCOPE,
NON_GOALS, CONSTRAINTS, VALIDATION, OUTPUT, plus SCRUTINY, ownership, and
context. Before dispatching:

```text
sb issue show <ref>        # exact revision
sb issue validate <ref>    # structural validity
sb issue attest <ref> --outcome ready --policy <p> --attested-by <who>
sb issue claim <ref> --holder <who>   # atomic lease before mutation
sb issue resume <ref>      # Resume Capsule when continuing
```

Readiness is re-validated after any execution-relevant change. `sb issue edit
<ref> --title … --priority …` is metadata (no revision); `--contract
… --ownership … --context-refs … --scrutiny …` is execution-bearing (new
revision, readiness invalidated). Graph moves (`sb issue relate / unrelate
--from <a> --to <b> --kind …`) never touch the contract. A claim is an atomic
lease, not an assignee label, and mutation requires the writer lease.

## Coordinator methodology (ADR §§51, 74)

A root/coordinator Journal contains programme decisions, cross-child blockers,
integration milestones, child status transitions, critical path, pending
questions, dispatch/retry decisions, and release gates. A coordinator
checkpoint references child Issues, child states, latest child checkpoints,
active claims, active Specialists, pending asks, and important receipts/PRs.
Do not duplicate full child Journal bodies.

Coordinator workflows periodically inspect children, claims, pending asks, new
results, blockers, provenance, and release gates, and journal only material
root-level state. No giant rewritten root description. No child transcript
duplication.

Live inspection:

```text
sb issue children <ref>             # child Issues and states
sb issue tree --root <ref>          # hierarchy
sb issue show <ref>                 # exact revision and readiness
sb issue resume <ref>               # Resume Capsule: revision, checkpoint, delta, claim, blockers, child status, pending asks, provenance state
sb journal since <ref> <cursor>     # delta reads only
sb journal show <ref>               # bounded history reads
sb provenance trace <ref>           # what execution produced
sb issue validate <ref>             # readiness still current
```

## Journal kinds (ADR §73)

Canonical guidance:

```text
material fact
→ finding

architectural choice
→ decision

blocked condition
→ blocker

progress boundary
→ milestone

handoff
→ handoff

completed bounded run
→ result

ordinary useful annotation
→ note


authorized work changed
→ STOP
→ /planning
→ new Issue revision
```

Live verbs (append-only; notes never bump the revision):

```text
sb issue note <ref> "text" --kind note|finding|decision|blocker|milestone|handoff|result
sb journal append <ref> --kind finding|decision|blocker|milestone|handoff|result|checkpoint|compaction|note
sb journal checkpoint <ref>             # mechanical checkpoint at durable boundaries
sb journal since <ref> <cursor>         # delta reads only
sb journal show <ref> / sb journal render <ref>   # bounded history reads
sb issue note <ref> "…" --kind handoff  # continuation entry for the next worker
```

Ordinary workers journal high-signal durable facts only: a material finding, an
important decision, an external blocker, a meaningful milestone, a handoff, a
result, and a checkpoint. Do not journal every shell command, every tool call,
chain-of-thought, transient speculation, or routine exploration.

If authorized work changed, execution pauses → `/planning` → new Issue revision
→ new readiness attestation → execution resumes. Never smuggle new scope into
prompts, messages, or journal entries.

## Boundaries (ADR §54)

- **Journal != Issue.** Progress entries never modify the contract; only a
  planning revision changes executable authority.
- **Journal != Memory.** Findings never auto-become reusable truth.
- **Messages != authority.** Channel messages coordinate but never silently
  change the contract.
- **Provenance != progress notes.** Executor output is a claim; record what
  execution produced via `sb provenance dispatch <ref>` / `sb provenance trace
  <ref>`, separate from journal progress.

The Issue owns execution authority; the Journal records what happens. Progress
update → Journal. Finding → Journal. Decision within existing authority →
Journal. Blocker → Journal. Result → Journal. Handoff → Journal. But SCOPE
changes, SUCCESS changes, CONSTRAINT changes, VALIDATION changes, OUTPUT
changes, and material scrutiny/ownership changes require stop execution →
`/planning` → new Issue revision → readiness → continue. Do not use Journal
entries to bypass contract revision.

## Resume (ADR §55)

Normal continuation reconstructs from current Issue revision plus latest
checkpoint plus Journal delta since checkpoint plus claim plus blockers plus
child status plus pending asks plus provenance state. This produces the Resume
Capsule. A worker should not need the previous chat transcript.

## Handoff and closeout (ADR §75)

Handoff = Issue stays authority + bounded Journal handoff/checkpoint entry +
blockers + known pending work + provenance refs; the next worker restarts from
`sb issue resume`. Long transcripts do not belong in the Journal. Before exit,
closeout, or compaction, write the mechanical checkpoint first (`sb journal
checkpoint <ref>`).

Before closure: SUCCESS satisfied, VALIDATION complete, required OUTPUT exists,
material result durable, important decisions/findings durable, provenance
sufficient, and no incompatible blocker remains. Then write structured Closure
(`sb issue close <ref> --outcome <o> --reason <r>` with result, receipt,
validation, artifact refs; then `sb issue release <ref> --holder <who>`). Do
not close solely because a commit exists.

No active retired commands. Historical references, where unavoidable, are
explicitly marked as history ("retired", "formerly", "migration") and never as
live workflow. Contract repair always routes through `/planning`.
