# Using Specialists (canonical Substrate-native doctrine)

Specialists is one execution backend inside XTRM. XTRM owns the work contract,
continuity, and system-level coordination. Specialists owns specialist selection,
job execution, retained results, role boundaries, and specialist-specific review loops.

Do not use this skill as a substitute for `/using-xtrm`, `/planning`, or the
multiplexing coordination surface.

## Dispatch chain (§34)

```text
ready Substrate Issue
     ↓
claim
     ↓
specialist_dispatch(issue_ref)
     ↓
exact revision / hash pinned
     ↓
NativeActivationHost
```

Specialists do not receive Beads (retired Beads term for the old work item). The dispatch argument is the Substrate Issue
ref (`issue_ref`); the exact Issue revision (and its readiness attestation) is
pinned at dispatch so the specialist executes one unambiguous contract. Where the
installed CLI still spells the tracked-work flag `--bead`, pass the Issue ref
there — the flag name is transitional, the Issue revision is authoritative.
Ad-hoc `--prompt` runs are untracked by definition: never use a prompt to smuggle
requirements that belong in the Issue contract.

## Contract precondition

If Substrate reports this repository is uninitialized: run `sb init`.

```text
sb init
```

Never guess the only project, invent a project id, or manually create/link
during normal work. Contract changes use only `sb issue edit` and
`sb plan apply`; progress uses the Journal.

A specialist receives a durable XTRM work item. A ready Issue revision is the executable
contract, and it must already be usable before dispatch:

1. `sb issue show <ref>` — read the exact revision: PROBLEM, SUCCESS, SCOPE,
   NON_GOALS, CONSTRAINTS, VALIDATION, OUTPUT, plus SCRUTINY, ownership, and
   context. A draft, incomplete, stale, or code-contradicted Issue is not
   executable.
2. `sb issue validate <ref>` and attestation
   (`sb issue attest <ref> --outcome ready --policy <p> --attested-by <who>`) —
   readiness before execution, re-validated after any execution-relevant change.
3. `sb issue claim <ref> --holder <who>` before dispatching work that mutates;
   `sb issue release <ref> --holder <who>` when done. A claim is an atomic lease,
   not an assignee label, and mutation requires the writer lease.

If the contract is insufficient, repair it through `/planning` (new revision plus
new readiness attestation). Never patch missing scope into a dispatch prompt, a
channel message, a journal entry, or a specialist instruction.

## Choose a specialist when the role adds value

Resolve the live set with `specialists list --full` and `sp help` before relying
on remembered roles or flags; the installed registry is authoritative. Typical
shapes: explorer (read-only mapping), debugger (unknown cause first), executor
(scoped implementation), reviewer / seconder / test / security-auditor gates,
researcher, documentation/release roles.

Do small, obvious work in the current session when delegation costs more than it
saves. XTRM is multi-agent by design; that does not mean every edit needs a child.

## Job lifecycle

```text
contract ready
 -> select live specialist
 -> dispatch against the Issue ref (revision pinned)
 -> observe job state / evidence (ps / feed / log / result)
 -> consume the persisted result
 -> verify claims against current tree / tests / runtime
 -> run required review / test / security follow-up
 -> record provenance, journal, then publish or hand back
```

Before dispatching dependent work, re-derive the base: working tree clean enough
for the next lane, prior required commits/results present, correct
branch/worktree selected, no stale job or ownership assumption. Stale-base
dispatch is a coordination defect — fix the state before adding another worker.

Do not busy-poll. Use the runtime's wait/feed/result mechanisms and XTRM
continuation facilities. If context pressure threatens the coordinator, persist
job IDs, states, pending findings/replies, and the next action, then hand off
through the resume surface — never keep a half-understood swarm alive inside a
failing context window.

## Findings, journal, and authority (§§15–17, §34)

Specialist execution findings belong in the Issue Journal where durable continuity
warrants them, using the landed kinds:

```text
sb issue note <ref> "text" --kind note|finding|decision|blocker|milestone|handoff|result
sb journal append <ref> --kind finding|decision|blocker|milestone|handoff|result|checkpoint|compaction|note
sb journal checkpoint <ref>     # mechanical checkpoint at durable boundaries
sb journal show <ref> / sb journal since <ref> <cursor> / sb journal render <ref>
```

Canonical kind mapping (ADR §73):

```text
material fact
→ finding

architectural choice
→ decision

blocked condition
→ blocker

progress boundary
→ milestone

handoff
→ handoff

completed bounded run
→ result

ordinary useful annotation
→ note

ordinary annotation
→ note

authorized work changed
→ STOP
→ /planning
→ new Issue revision
```

A continuation entry uses the handoff kind directly:

```text
sb issue note <ref> "…" --kind handoff
```

 finding (observation) · decision (choice + reason) · blocker (external
dependency) · milestone/checkpoint (progress boundary) · handoff (continuation)
· note (ordinary annotation). Do not journal every shell command. Notes are
append-only and never bump the Issue revision.

Authority invariants (non-negotiable):

- A Specialist result does not modify the Issue contract. **Journal != Issue.**
- Findings never auto-become reusable truth. **Journal != Memory.**
- Channel messages coordinate; they never silently change the contract.
  **Messages != authority.**
- Executor summaries are claims; record what execution produced via provenance
  (`sb provenance dispatch <ref>`, `sb provenance trace <ref>`), separate from
  journal progress. **Provenance != progress notes.**
- Scope-changing findings route back through planning: stop → `/planning` →
  new Issue revision → new readiness attestation → resume. Never smuggle new
  scope into prompts, messages, or journal entries.

## Resume, compaction, handoff (§§18–20 as applied to specialists)

A resumed specialist lane restarts from `sb issue resume <ref>` (Resume Capsule:
revision, checkpoint, journal delta, claim, blockers, child status, pending asks,
provenance state) plus `sb journal since <ref> <cursor>` — never from chat
history, never from a full-history dump. A fresh worker reaches the executable
state from Issue revision + capsule + journal delta alone, without previous chat history.

Before compaction, exit, handoff, or close: mechanical checkpoint first
(`sb journal checkpoint <ref>`; durable even if everything after fails),
optional semantic enrichment after, then continue from the capsule. If a summary
disagrees with Issue/Journal/provenance state, durable Substrate state wins.

Handoff = Issue stays authority + bounded Journal handoff/checkpoint entry +
blockers + known pending work + provenance refs; the next worker uses the
capsule. Long transcripts do not belong in the Journal.

## Production changes and closeout

For a production diff, preserve the project-required review and validation gates;
resolve the exact set from the current registry and contract, never from memory.
At minimum: implementation/debug evidence, real tests or explicit test evidence,
independent review where required, security review where warranted, and no
unresolved findings hidden by the final summary. Reviewer/seconder findings
require a fix loop when valid — never reinterpret a failing gate as advisory
because the diff looks plausible. Classify test failures (in-scope regression /
pre-existing / infrastructure) before touching unrelated code.

Close through the lifecycle surface only after validation + provenance +
checkpoint: `sb issue state <ref> done` (or the
`close|reopen|defer|cancel|archive` aliases; `sb issue close <ref> --outcome
<o> --reason <r>` writes the structured Closure with result, receipt,
validation, artifact refs), then release the claim.

Before closure: SUCCESS satisfied, VALIDATION complete, required OUTPUT exists,
material result durable, important decisions/findings durable, provenance
sufficient, and no incompatible blocker remains. Do not close solely because a
commit exists.

## Coordinator duties (ADR §74)

Coordinator workflows periodically inspect children, claims, pending asks, new
results, blockers, provenance, and release gates, and journal only material
root-level state. No giant rewritten root description. No child transcript
duplication. Do not duplicate full child Journal bodies. Inspect with
`sb issue children <ref>`, `sb issue tree`, `sb issue show <ref>`,
`sb issue resume <ref>`, `sb journal since <ref> <cursor>`, and
`sb provenance trace <ref>`.

## What this skill deliberately does not own

- Contract authoring and repair → `/planning`.
- Full worker loop, authority stack, classification rules → `using-xtrm`.
- Cold-start / takeover / context-pressure handoff → `starting-and-resuming-work`.
- Peer messaging and wake/reply → multiplexing surface.
- Code-graph evidence strategy → gitnexus surface.
- Service-knowledge skill machinery → that system's own skill (out of scope here).
