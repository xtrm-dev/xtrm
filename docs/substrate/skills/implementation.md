# Implementation (canonical Substrate-native doctrine)

Implementation executes a ready Issue revision. It does not author authority, and it
does not smuggle authority changes inside progress notes.

## Authority the implementer obeys (§§13–17)

If Substrate reports this repository is uninitialized: run `sb init`.

```text
sb init
```

Never guess the only project, invent a project id, or manually create/link
during normal work.

The executable contract is a ready Issue revision: PROBLEM, SUCCESS, SCOPE,
NON_GOALS, CONSTRAINTS, VALIDATION, OUTPUT, plus SCRUTINY, ownership, and context.
Before touching code:

```text
sb issue show <ref>        # exact revision
sb issue validate <ref>    # structural validity
sb issue claim <ref> --holder <who>   # atomic lease before mutation
sb issue resume <ref>      # Resume Capsule when continuing
```

Readiness is attested (`sb issue attest <ref> --outcome ready --policy <p>
--attested-by <who>`) and re-validated after any execution-relevant change.
`sb issue edit <ref> --title … --priority …` is metadata (no revision); `--contract
… --ownership … --context-refs … --scrutiny …` is execution-bearing (new revision,
readiness invalidated — use `--expected-revision N` for guarded writes).
Graph moves (`sb issue relate / unrelate --from <a> --to <b> --kind …`) never
touch the contract.

A fresh worker reaches the executable state from Issue revision + capsule +
journal delta alone, **without previous chat history**.

## During work: typed journal continuity (§15, §35)

```text
finding                                 → Journal finding
important architectural choice          → Journal decision
external dependency preventing progress → Journal blocker
meaningful completion boundary          → Journal milestone / checkpoint
continuation for the next worker        → Journal handoff
completed bounded run                   → Journal result
ordinary human annotation               → Journal note
```

Canonical kind mapping (ADR §73):

```text
material fact
→ finding

architectural choice
→ decision

blocked condition
→ blocker

progress boundary
→ milestone

handoff
→ handoff

completed bounded run
→ result

ordinary useful annotation
→ note


authorized work changed
→ STOP
→ /planning
→ new Issue revision
```

Live verbs (append-only; notes never bump the revision):

```text
sb issue note <ref> "text" --kind note|finding|decision|blocker|milestone|handoff|result
sb journal append <ref> --kind finding|decision|blocker|milestone|handoff|result|checkpoint|compaction|note
sb journal checkpoint <ref>             # mechanical checkpoint at durable boundaries
sb journal since <ref> <cursor>         # delta reads only
sb journal show <ref> / sb journal render <ref>   # bounded history reads
sb issue note <ref> "…" --kind handoff  # continuation entry for the next worker
```

Do not journal every shell command or transient thought. The Journal must remain
useful as bounded durable continuity: one observation per entry, choices with
reasons, blockers with the external dependency named, boundaries with what
completed and what remains.

## Authority changed? Stop (§16)

If SCOPE, SUCCESS, NON_GOALS, CONSTRAINTS, VALIDATION, OUTPUT, ownership, or
scrutiny must change:

```text
execution pauses
    ↓
/planning
    ↓
Issue revision
    ↓
old readiness invalidated
    ↓
new readiness attestation
    ↓
execution resumes
```

Never silently put the new scope into the Journal, a worker prompt, a channel
message, a handoff note, or a specialist instruction and continue as if
authorization had not changed.

## Invariants the implementer states, not implies

- **Journal != Issue.** Progress entries never modify the contract; only a
  planning revision changes executable authority.
- **Journal != Memory.** A finding may later become a memory candidate; it does
  not automatically become reusable truth. No `remember`-style capture inside
  the Journal.
- **Messages != authority.** Channel messages coordinate but never silently
  change the contract.
- **Provenance != progress notes.** Executor output is a claim; record what
  execution produced via `sb provenance dispatch <ref>` / `sb provenance trace
  <ref>`, separate from journal progress.
- Mutation requires a live claim on the Issue (`sb issue claim` / `sb issue
  release`); a claim is not an assignee label. Substrate provides no
  workspace-exclusion guarantee: the Specialists activation layer owns workspace
  exclusion.

## Validate, checkpoint, hand off or close (§§17, 19–20)

1. Run the contract's VALIDATION; classify failures (in-scope regression /
   pre-existing / infrastructure) before touching unrelated code.
2. Record provenance, then mechanical checkpoint (`sb journal checkpoint <ref>`)
   before handoff, close, compaction, or exit — mechanical state first, semantic
   enrichment optional and never a substitute. If a summary disagrees with
   Issue/Journal/provenance state, durable Substrate state wins.
3. Handoff = Issue stays authority + bounded Journal handoff/checkpoint entry +
   blockers + known pending work + provenance refs; the next worker restarts
   from `sb issue resume`. Long transcripts do not belong in the Journal.
4. Close via the lifecycle surface
   (`sb issue state <ref> done`, or the
   `close|reopen|defer|cancel|archive` aliases; `sb issue close <ref> --outcome
   <o> --reason <r>` writes the structured Closure with result, receipt,
   validation, artifact refs) after validation + provenance +
   checkpoint, then release the claim (`sb issue release <ref> --holder <who>`).

Before closure: SUCCESS satisfied, VALIDATION complete, required OUTPUT exists,
material result durable, important decisions/findings durable, provenance
sufficient, and no incompatible blocker remains. Do not close solely because a
commit exists. Contract changes use only `sb issue edit` and `sb plan apply`;
progress uses the Journal.

Ordinary workers journal high-signal durable facts only: a material finding, an
important decision, an external blocker, a meaningful milestone, a handoff, a
result, and a checkpoint. Do not journal every shell command, every tool call,
chain-of-thought, transient speculation, or routine exploration.

Coordinator workflows periodically inspect children, claims, pending asks, new
results, blockers, provenance, and release gates, and journal only material
root-level state. No giant rewritten root description. No child transcript
duplication.

No active Beads commands. Historical Beads references, where unavoidable, are
explicitly marked as history ("retired", "formerly", "migration") and never as
live workflow.
