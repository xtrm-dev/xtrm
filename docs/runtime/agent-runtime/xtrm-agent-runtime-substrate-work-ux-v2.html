3. Claimed Issue → Issue Task Plan

Substrate remains the durable work authority. The useful pi-tasks model becomes an Issue-bound execution plan instead of a second task database.

sb issue claim XTRM-341
        │
        ▼
claim accepted
        ├─ bind exact Issue revision
        ├─ create/resume IssueTaskPlan
        └─ expose task tools + guidance
                 │
                 ▼
        agent decomposes work
        #1 inspect
        #2 implement
        #3 integrate
        #4 validate
                 │
                 ▼
        persistent task strip above composer
ObjectMeaningAuthority
Substrate IssueWhat work is authorized.Durable work authority
Issue Task PlanHow current execution decomposes the Issue.Planning only
TaskSmall local step with dependencies/status.No independent scope authority
Child IssueIndependent durable work discovered during execution.Own revision/readiness/claim
If a local task needs independent ownership, a separate claim, a different work contract, cross-session scheduling or durable scope beyond the current Issue, promote it to a real child Issue.

6. Resume / revision model

Issue XTRM-341 rev 4
  └─ TaskPlan current=#3

Issue edited → rev 5
  └─ TaskPlan becomes stale

Agent must:
  compare contract delta
  update/add/cancel local tasks
  reconcile plan with rev 5

Task Plan survives claim renewal and controlled handoff. Resume reconstructs Issue, claim, current task, dependencies and relevant Journal/provenance without conversation memory.

7. xtrm-intercom

Adopt the mature working behavior of nicobailon/pi-intercom and alonw0/pi-claude-link behind one first-party capability: presence/roster, aliases, scoped routing, send/ask/reply, pending asks, message IDs and dedupe, mailbox semantics, receipts, cancellation, superseding, attachments, safe active-session injection, Claude registry/socket interoperability and Pi↔Claude round trips.

Interactive direct messaging can use the transport directly. Governed Chain communication still enters Channels. Intercom is not workflow authority.

8. xtrm-background

Borrow only the mature background process subset from pi-background-tasks: start, status, bounded logs, full-output reference, stop, rerun, completion events and optional host wake. Do not adopt Fusion, delegated-agent workflow or provider overrides.

Task lifecycle       pending → in_progress → completed
Background lifecycle queued → running → exited | failed | stopped

A task may reference a background job.
A process exit does not complete the task.

10. Python kernel

The Python kernel is persistent for this session.
Prefer it for iterative structured analysis and calculations.
Reuse variables, imports and functions.
Keep visible output bounded.
Persist workflow-relevant results as durable evidence.
Kernel state is not durable work state.
The kernel is not a sandbox.

11. End-state invariants

Substrate Issue says WHAT work is authorized.
Issue Task Plan says HOW the current Issue is executed.
Journal says WHAT HAS HAPPENED.
Provenance says WHAT execution durably produced.

A local task is not a hidden Issue.
A completed task is not a completed Issue.
A background process is not a task.
An intercom message is not user authority.
A tool existing is not a capability grant.
The TUI renders state; it does not own state.

XTRM agents know these rules by default.
