Premortem: substrate_design_it.md (Bozza rev. 12)

Frame: it is December 2026. Substrate has failed. The 5-package monorepo
(core/substrate/channels/specialists/console) exists. The daemon
runs. Operators are still using bd + sp + GitHub for daily work.
Why?

---

The single underlying assumption

Architecture coherence in one designer's head will transfer to other operators
through schemas, stage gates, and clean cutover — and that this will deliver
operator relief faster than shipping targeted patches against the existing
bd+sp stack while substrate is being built in private.

Every one of the 9 failure stories below is a special case of this assumption.

---

The 9 reasons it could fail

Each was deep-dived by an independent overthinker (gpt-5.5) run; raw outputs in
out-01.md through out-09.md.

1. Stage 0 is not a stage — it's the hardest product in the system

*(out-07)*

Stage 0 ships daemon + IPC protocol + SQLite migrations + identity/transactions
+ restart-stable session + cross-package schema registry + emitter idempotency.
That's not foundation — that's the kernel. Every later stage waits on it. There
is no kill switch, no degraded mode, no coexistence shim. Stage 0 either takes
8+ weeks or ships unsound and leaks races into every container.

Either way, the calendar burns before stage 4 can show an operator anything.

2. Design drift outran implementation

*(out-01)*

Rev 12 calls itself converged but the same pattern that produced rev 1→12 is
still wired in: implementation surprise → new doc section → new runtime concept
→ "convergence". There is no freeze rule. Each edge case becomes design input
instead of a merged PR. The doc has prestige; bugs become evidence the doc
needs one more section. Runtime never hardens.

3. The clean cutover never cuts

*(out-08)*

Stage 13 is the only path to production truth (claims, deps, memories, close
semantics). There is no coexistence shim — operators must choose bd or
substrate. They will choose bd because work cannot pause. Substrate then
learns bd's real behavior at the migration (bd kv, FTS5 quirks, dep-graph
edges, Stop-hook claim release, memory-ack batch closes) — exactly when there
is no rollback. Each gap blocks cutover instead of becoming one bridged edge.

4. Total rebuild instead of five targeted fixes

*(out-09)*

The five real pains (claim weakness, chain implicitness, late collision discovery,
weak memory recall, unstructured bd create) get bundled behind daemon + store +
socket + packages + SDK + console. The first useful operator fix arrives at
stage 7 — after the existing pain has continued for six months. Five narrow
patches against bd+sp would have shipped relief inside stage 0's calendar
window without delaying a single line of substrate plumbing.

5. The node-coordinator is a load-bearing fiction

*(out-02)*

participant_id, job_id, can_open_containers, autonomy_json, pulse
emitter, capability model, SDK — all assume an autonomous reader. No stage in
the 13-stage plan gives the node-coordinator its own delivery gate. It is
"future semantic layer." Without one process that reads a pulse, evaluates
autonomy_json, opens a child container, journals, survives restart, and
respects denial — the SDK is wrappers, the pulse emitter is logging, the
capability model is dead schema. Architecture sells autonomy and ships
bureaucracy.

6. The chain coordinator is over-specified

*(out-05)*

One name hides three products: reducer, judge, supervisor. coordinator_model:
null is not a cost setting — it's a semantics change. The no-LLM reducer
passes clean chains and fails exactly where the coordinator was supposed to add
value (borderline evidence). LLM mode works but costs blow up at substrate's
chain volume. The runtime shape ends up as three modes:
cheap-no-judgment / expensive-with-judgment / off. By December most operators
have chosen off.

7. The two-tier story has no v0 for the top tier

*(out-06)*

"No FK cross-domain, 1:1 row transfer, trivial projection." Trivial hides
identity stability across machines, reader-side lineage reconstruction from
opaque IDs across the network, conflict handling on team-level writes, evidence
ref resolution when the referenced file lives on a different laptop, and
write-coalescing for high-volume xtrm_forensic_events. None of these has a
v0. The bottom tier ships solo-user. The top tier never starts. The
team/company adoption story — which justified building five packages instead of
one — quietly dies.

8. Console deferred — substrate ships invisible

*(out-03)*

§16 says runtime models the entities; dashboard reveals them. §14 defers the
dashboard, lineage drawer, and AWS-agentcore observability to downstream
gitboard work. Stage 12 of the plan merges sp feed -f + sb feed -f — a
stream fusion, not an entity-aware dashboard. By December, chains exist in
SQLite with stable IDs, the collision matrix is populated, plan artifacts are
stored — and operators have no UI for any of it. They keep reading sp
feed and bd show. Substrate is backend truth nobody can see.

9. Author = implementer, no second eyes

*(out-04)*

The doc carries absorbed operator-notes, closed round-3 audits triaged by the
author, and an unanswered "questions for next agent" §14.1. The dialogue
throughout reads as a single mind in conversation with itself. The vocabulary
(seed/chain/wave/node/participant/job/tether/memory capability)
fits the author's mental model perfectly — which is exactly why nobody else can
operate it on first contact. Clean cutover then removes the familiar escape
hatch (bd+sp+GitHub) before the new mental model has been transferred to
anyone outside the author's head.

---

Cross-cutting patterns (the synthesis)

Reading the 9 deep-dives side by side, four meta-pathologies emerge that no
single reason captures:

A. The "deferral compound"

Every individual cure is deferred to "later": coexistence shim deferred, console deferred, top-tier deferred, node-coordinator demo deferred, external reviewers deferred. Each deferral is defensible alone. Stacked, they guarantee that no operator-perceptible value lands before stage 7 at the earliest, and the calendar runs out before that.

B. Invisible + irreversible + unfamiliar

Reason 8 (invisible), reason 3 (irreversible — no shim), and reason 9 (unfamiliar — author-shaped vocabulary) multiply. An operator who can't see substrate, can't fall back to bd, and can't intuit the model has zero reasons to switch. Each pathology amplifies the others. Fixing one is not enough.

C. Three abstractions are bundles, not entities

Node-coordinator (#5), chain coordinator (#6), and two-tier projection (#7) share one shape: one name hides multiple products with different semantics, cost curves, and UX. The system cannot ship any one of them coherently because each needs different stage acceptance criteria than the plan provides.

D. Stage acceptance ≠ operator adoption

Even when each stage technically ships (chain container exists, validator passes, collisions recorded), no operator decision cites substrate output as authority. Runtime entities exist but are operationally dead. The 13-stage acceptance criteria measure plumbing, not adoption.

R1 — Design drift outran implementation

Phase 1 - Initial Analysis

Design drift failure starts from pattern: new concern enters doc, becomes new runtime concept, gets labeled convergence. Substrate scope already spans daemon, socket, SQLite authority, five packages, container lifecycle, validator, channels, tether, collision matrix, memory relevance, pulse layer, skill injection, participant SDK, console, migration. Serial sequencing makes drift lethal: stage 0 gates all later value.

Main risk: implementation learning loop routes surprises into architecture revision, not shipping slice. Each edge case becomes design input. Runtime never hardens.

Phase 2 - Devil's Advocate

Counterpoint: absorbing concerns can prevent bad foundations. Chain coordinator, skill injection, issue relationships may be real missing primitives. Cutting scope too early could ship weak substrate requiring rewrite.

But failure reason stays valid because plan has no freeze rule. No coexistence shim, no deferred console, no migration bridge, serial stages, same author/implementer. No external brake. Design has prestige; bugs become proof doc needs one more section.

Phase 3 - Synthesis

Root problem not ambition alone. Root problem: no boundary between architecture discovery and runtime delivery. Substrate treats implementation edge cases as requirements intake. That makes stage completion unstable. Stage 0–4 must become thin, frozen, ugly, measurable runtime before any new abstractions land.

Phase 4 - Final Refined Output

Recommendation: freeze substrate MVP around daemon, state.db, socket, issue validator, chain container only. New concerns become post-MVP beads unless blocking running chain container in production.

Final Answer

The Failure Story

June 2026 started with substrate_design_it.md at Bozza revisione 12 and “converged.” Stage 0 began: daemon, state.db, Unix socket, five-package client boundary. First implementation week exposed protocol versioning, crash recovery, opaque-ID correlation, and SQLite migration questions. Instead of cutting scope, rev 13 added invariants and daemon lifecycle rules. Stage 0 took all June and most of July.

July and August should have delivered stage 1 issue schema, stage 2 channels, stage 3 tether, and stage 4 chain container. Instead, stage 1 hit §6.7 issue-relationship ambiguity, stage 2 raised channel/domain-table ownership concerns, and stage 4 revived coordinator semantics: fresh-context spawning, kill+respawn, journal gap detection, coordinator_model: null. Each edge case became design work. Runtime PRs stalled behind “one more clarification.” Validator and chain lifecycle stayed demo-level; no operator used sb container ps chain:X.

September through December collapsed into permanent draft mode. Collision matrix, plan artifacts, epic/wave kinds, advisor invites, small-model tether relevance, reconciler, console feed, and bd migration all depended on unfinished earlier stages. Since there was no coexistence shim, cutover risk rose every month. Operators kept using sp+bd+GitHub because it existed. Substrate became architecture vocabulary pasted onto tribal practice, not runtime substrate.

The Underlying Assumption

Designer assumed implementation discoveries could keep expanding architecture without consuming delivery runway or invalidating MVP freeze.

Early Warning Signs

- Revision velocity beats shipped runtime velocity: two or more new doc sections/operator-note absorptions land after stage 0 starts while daemon + issue validator + chain container remain unused in daily work.
- Implementation bugs get resolved as design revisions or new beads instead of merged code: “needs section,” “under-drilled,” or “post-revision clarification” appears more often than runtime PRs closing stage acceptance criteria.

R5 — Node-coordinator is load-bearing fiction

Phase 1 - Initial Analysis

Node-coordinator underwrites too much. Participant SDK, capability model, autonomy_json, pulse emitter, identity layers all assume autonomous reader exists.

Sequencing hides risk. 13 stages never give node-coordinator own delivery gate. Chain-only runtime ships first; node remains future semantic layer.

Phase 2 - Devil's Advocate

Maybe node not needed for v1. Orchestrator can fake scheduling. Human can approve child containers. Daemon can own mechanical scheduling.

Problem: then architecture sells autonomy but ships bureaucracy. Dead abstractions stay because future node “will need them.” Users pay complexity now for entity absent later.

Phase 3 - Synthesis

Failure mode: not technical impossibility alone. Governance failure. Design made node-coordinator load-bearing, then omitted near-term proof. Every abstraction got accepted as “for autonomy,” while autonomy never passed one end-to-end scenario.

Real test: one long-running coordinator reads pulses, evaluates policy, opens child container, journals why, survives restart, respects denial. If absent by Stage 4, stop expanding SDK/capability/identity surface.

Final Answer

To avoid blocking, implementer kept node-coordinator out of scope and said chain containers would prove runtime shape first. By August, Stage 4 shipped chain lifecycle and fresh-context chain coordinator behavior, but only orchestrator read state. participant_id, job_id, can_open_containers, autonomy_json, and pulse idempotency landed as schema/API commitments without one process using them to autonomously open child containers.

September–October exposed semantic scheduling as real product work, not plumbing. Every concrete node use case needed policy exceptions: when can coordinator open child wave, invite advisor, escalate issue, mutate plan artifact, or lease worktree? autonomy_json became permission DSL without owner, tests, or UX. Milestones kept moving node to “next quarter” while stages 7–12 added collision matrix, epic/wave containers, advisor rules, tether relevance, reconciler, and console feed. Each feature assumed future autonomous reader, but production still had orchestrator plus human convention.

By December, Substrate had one source of truth and one real reader: orchestrator. Human used console as passive dashboard. Node-coordinator never existed as long-running actor. Participant SDK became wrappers for scripts and specialists. Pulse emitter became logging. Capability model became dead schema. Team learned new runtime vocabulary but still coordinated by tribal judgment, now with more tables and stricter gates.

The Underlying Assumption

Designer assumed autonomous semantic scheduling could be postponed because surrounding runtime contracts would make node-coordinator implementation straightforward later.

Early Warning Signs

- No executable demo by Stage 4 where node process reads pulse, evaluates autonomy_json, opens child container, records journal entry, survives restart, and denies forbidden action.
- PRs keep adding participant_id, job_id, can_open_containers, emitter/pulse, or SDK surfaces while every production caller remains orchestrator-owned.

R6 — Chain coordinator over-specified

Phase 1 — Initial Analysis

Chain coordinator failed because one name hid multiple products: reducer, judge, supervisor. coordinator_model: null changed semantics, not cost setting. Borderline evidence needed judgment, so no-LLM mode failed where value mattered. LLM mode worked better, cost exploded. Off mode became default.

Phase 2 — Devil's Advocate

Maybe coordinator could survive if scoped to high-risk chains only. Maybe deterministic reducer handles normal chains, LLM handles exceptions. But design promised one always-on entity across many chains per day. That promise forced cost path into hot path, then operators rejected whole abstraction.

Phase 3 — Synthesis

Core flaw: capability bundle too dense. Fresh-context spawning, kill+respawn, journal gap detection, release atomicity, pulse hygiene, memory distillation, and judgment should not ship as one runtime shape. Split abstraction: deterministic chain monitor first; optional adjudicator later; memory closeout separate.

Phase 4 — Final Refined Output

Recommendation: demote chain coordinator from container judge to auditable reducer. Make LLM adjudication explicit, metered, opt-in per disputed transition. Never hide semantic change behind coordinator_model: null.

Final Answer

The Failure Story

June–July went into stage 0 and stage 4 plumbing: daemon, socket, chain container lifecycle, journal events, coordinator.release, respawn hooks. §4.3 kept changing because every bug looked like missing coordinator behavior: fresh-context spawn for drift, gap detection for crashes, pulse hygiene for cross-chain leaks, memory distillation at close. By August, chain coordinator existed, but only as two half-working paths: coordinator_model: null reducer that could replay events, and LLM judge that could interpret messy evidence.

September dogfood exposed break point. No-LLM reducer passed clean chains but failed borderline cases: partial test logs, ambiguous collision warnings, missing release evidence, specialists claiming “done” with dirty worktrees. Those were exact moments coordinator was supposed to decide. Operators stopped trusting ready/closed transitions unless LLM mode reviewed them. Cost jumped from near-zero to per-chain spend across many chains per day, plus latency from fresh-context spawning and two-compaction context rebuilds.

October–November produced third runtime shape: coordinator off. Teams first disabled LLM mode for low-value chains, then disabled coordinator entirely after respawn bugs and false release blocks made it slower than tribal review. By December, “chain coordinator” meant cheap-no-judgment, expensive-with-judgment, or off, depending on operator mood. Console state became less trustworthy because lifecycle transitions no longer meant same thing across chains. Runtime entity never became production truth.

The Underlying Assumption

Designer assumed one coordinator abstraction could switch between deterministic reduction and semantic judgment without changing product semantics.

Early Warning Signs

- Dogfood metric: percentage of coordinator_model: null chains needing manual override for ready → closed or disputed coordinator.release; anything above 10% means reducer is not coordinator.
- Cost/latency metric: median coordinator tokens and wall time per chain rising faster than specialist work time, especially on borderline evidence chains.

The Underlying Assumption

Designer assumed local-first entities would become team/company entities by projection, without treating projection semantics as core runtime design.

Early Warning Signs

- No passing two-laptop Supabase demo by end of stage 0: same project, stable participant_id, one approval/comment, one evidence ref, lineage reconstructed from top tier.
- Top-tier notes still use words like “trivial,” “later,” or “1:1 row transfer” without schemas for conflict writes, evidence resolution, event coalescing, and identity derivation.

R2 — Stage 0 is the hardest product in the system

Phase 1 - Initial Analysis

Stage 0 carries hidden product: daemon, IPC protocol, migration system, locking, identity, transactions, versioning, restart behavior. Not foundation. Whole runtime kernel.

Serial dependency makes delay fatal. Stages 1–13 wait. If Stage 0 slips, validators, chain containers, lifecycle, channels, tether, collision matrix all compress or build on unstable base.

Core risk: Substrate tries replacing tribal practices with runtime entities, but first ships invisible plumbing. Operators see no value until Stage 4 minimum. Calendar burns before feedback.

Phase 2 - Devil's Advocate

Maybe robust daemon worth cost. Shared SQLite over socket prevents five packages corrupting state. Early shortcut could poison whole architecture.

Counterpoint: six-month window cannot absorb custom IPC plus schema governance plus multi-client semantics. Existing bd→Dolt lesson warns against networked-store complexity, but plan repeats pattern locally. Unix socket smaller than network, not simple.

Bigger critique: Stage 0 has no kill switch. No coexistence shim. No degraded mode. If daemon unstable, everything waits or patches around it.

Phase 3 - Synthesis

Failure reason strong. Stage 0 not one stage; it is database server, migration coordinator, process supervisor, domain boundary contract, event deduper. Each concern crosses packages. Each needs tests before runtime entities can be trusted.

Most likely failure shape: either perfectionism delays visible substrate, or premature “good enough” leaks races into containers. Both end same: runtime entities never feel real. Operators keep using tribal sp+bd+GitHub flow because Substrate remains infrastructure project, not work system.

Recommendation: cut Stage 0 scope to smallest append-only local event log plus one write API, then ship Stage 1–4 behind it. Push schema registry, pulse idempotency, multi-domain transaction semantics, and restart-stable identity hardening until chain container proves daily value.

Final Answer

The Failure Story

June 2026 went into Stage 0 design closure: daemon lifecycle, file-lock launch, Unix socket framing, project registration, state.db ownership, schema registry. No operator-facing runtime entity shipped. By late July, schema migrations across core/substrate/channels/specialists/console became main blocker: each package wanted tables, but no FK cross-domain meant opaque IDs needed extra reconciliation rules. First “working” daemon could start and answer requests, but restart behavior orphaned active jobs and broke participant/job identity assumptions.

August became transaction month. Container open, emitter/pulse dedup, and channel writes all needed serialized writes with idempotency keys. Race tests found duplicate chain containers when two clients opened same worktree lease. Fixes pushed socket protocol versioning and migration locks into Stage 0. R3 — Clean cutover never cuts

Phase 1 - Initial Analysis

Substrate fails because adoption depends on one late Big Bang migration. Stage 13 carries production truth: active issues, claims, memories, deps, worktrees, close semantics. Earlier stages produce architecture, not workflow replacement.
