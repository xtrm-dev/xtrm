The chain coordinator is over-specified. §4.3 is the most-contested entity across rev 10, 11, 12. It's described as "a permanent judge of a transient container" with: fresh-context spawning, kill+respawn semantics, journal-based gap detection with state snapshot, `coordinator_model: null` no-LLM reducer mode for cost-zero operation, atomicity via a specific evidence kind (`coordinator.release`), context-window bounded to ~2 compactions, `autonomy_json.can_emit` capability fields, cross-chain hygiene by pulse, memory distillation at close. The design promises these are all the same entity with switchable behaviors. Six months in, the LLM path turned out to cost ~$X per chain (substrate runs many chains per day), the no-LLM reducer turned out to be insufficient for borderline-evidence judgments — exactly the cases where the coordinator was supposed to add value — so operators turned off the no-LLM mode, costs spiked, and operators turned off the coordinator entirely. What the design promised was one entity ended up as three different runtime shapes (cheap-no-judgment, expensive-with-judgment, off), each with different bugs, and the chain coordinator stopped being a useful abstraction.
